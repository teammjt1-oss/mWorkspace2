# 관리 모듈 이식: 조사 결과

2026-09-24 기준으로 파악한 내용을 정리한다. 계획서 작성 절차는 [admin-이식-계획작성.md](admin-이식-계획작성.md)를 따른다.

## 한눈에 보기

- 원본: admin.team-mjt.com. Nuxt 앱이고 소스는 `/Users/pc/Desktop/mWorkspace`에 있다.
- 목표: Next.js로 옮긴다. 모델만 정의하면 목록과 상세 화면이 자동으로 나오는 공통 모듈로 만든다.
- 운영 데이터는 Supabase Postgres에 있다. lowDB는 개발용이다.
- 원본의 파일 삭제와 업로드 라우트에 인증이 없다. **원본에서 먼저 막아야 한다.** (아래 "보안 구멍" 참고)
- 스타터에는 Payload, "스타터 구조 결정" 문서, design-system 패키지, 인증이 없다.

## 이미 정한 것

- **데이터 규모**
  - 대부분의 표는 100~200건이다. 전체를 불러와 클라이언트에서 조회하는 원본 방식을 유지한다.
  - 1만 건까지 늘 수 있는 표 세 개만 예외로 처리한다.
- **첫 대상 모델**: 역할이나 등급으로 시작한다.
- **이름**
  - `@repo/*`를 `@mjt/*`로 바꾼다.
  - 관리자 페이지는 새로 `apps/admin`을 만든다.
  - `apps/web`은 그대로 둔다. 공식 홈페이지(`official`)를 어디에 둘지는 나중에 정한다.
- **원본의 변화**: 이식하는 동안 원본은 크게 바뀌지 않는다. 원본을 기준으로 삼는다.
- **데이터 이전**: 하지 않는다. 이식본은 빈 DB로 시작한다.

## 원본 구조

### 앱 구성

- `apps/mjt-admin`이 admin.team-mjt.com을 서빙한다.
- Nuxt layers로 `mjt-admin` → `base-mjt` → `base2` 순서로 extends한다. 운영 빌드는 base-mjt와 base2를 github 저장소에서 받는다.
- 배포는 Netlify로 한다.

### base2 규모 (약 34,600줄)

| 층          | 줄 수     |
| ----------- | --------- |
| m           | 약 16,200 |
| View        | 약 7,400  |
| composables | 약 4,500  |
| Field       | 약 4,400  |
| lib/models  | 약 2,200  |

### 모델 엔진 (`base2/lib/models`, 14개 파일, 2,154줄)

- **핵심 파일**
  - `BaseModels2.ts`(694줄): 표 저장소. 목록, CRUD, 일괄 저장, SSR payload를 맡는다.
  - `BaseModel2.ts`(371줄): 행 모델. state 관리, 저장, 수정 여부 판정을 맡는다.
  - `BaseModels2.view.ts`(203줄): 조회와 URL 쿼리 변환을 맡는다.
  - `ORM.ts`(135줄): 타입 이름을 Field 컴포넌트로 바꾼다.
  - 그 밖에 `textSearch`, `identity`, `version`, `cachedRead`, `instance`, `env`, `types`, `seo`가 있다.
- **모델이 화면을 선언한다**: `자동필드ss`, `필터조건ss`, `정렬조건s`, `검색필드s`, `badges`, `요약s`.
- **반응성**
  - 원본 행은 Vue `Ref<Dto[]>`에 들어 있다.
  - `list`는 computed다. 삭제된 행을 빼고, 행마다 모델 객체를 한 번만 만들어 캐시하고, 정렬한다.
  - 행 객체는 바꿔 끼우지 않고 `Object.assign`으로 갱신한다.
- **로딩**
  - `GET {api}/{table}`을 부른다. 본문 열은 `?omit=`으로 뺀다.
  - 표 버전이 같으면 다시 받지 않는다. 캐시 TTL은 5초다.
- **조회**
  - `조회하기` 함수 하나가 검색 → 정렬 → 필터 순으로 처리한다.
  - 필터는 다른 표를 이어 붙여 계산한 값에 거는 JS 함수다.
  - 필터 축끼리는 AND로, 한 축 안의 여러 선택은 OR로 묶는다.
  - URL 쿼리(`?q=`, `?sort=`, `?f_<축>=`) 변환은 순수 함수여서 그대로 옮길 수 있다.
- **저장**
  - 신규 행은 `POST`, 기존 행은 `PUT`, 일괄 저장은 `/bulk`로 보낸다.
  - 삭제할 때는 목록에서 먼저 빼고, 실패하면 되돌린다.
  - 필드 단위 검증은 없다. `beforeSave()`가 유일한 관문이다.

### 폼과 Field

- `View/1.ts`가 모델의 `자동필드ss`에서 필드 목록을 만든다. `자동필드ss`가 없으면 getter와 setter를 반사해서 만든다.
- 컴포넌트는 이 순서로 고른다.
  1. `type`
  2. `options`가 있으면 `선택0`
  3. 값의 타입(문자, 숫자, 체크, 날짜)
  4. 문자
- Field 계약
  - 값은 `modelValue`와 `update:modelValue`로 주고받는다.
  - `readonly`를 받는다. `is-doing`은 선택 사항이다.
  - 나머지는 스펙의 `props`와 `items`로 받는다.
  - 버튼 필드는 값 없이 `onClick`, `label`, `icon`을 받는다.
- 모델 쪽 파일 80개에서 `타입지정` 사용 횟수 (합계 409):

| 1차  | 선택0 117, 문자 39, 숫자2 27, 체크 27, 숫자 18, 날짜 17, 버튼 15, 날짜2 7, 전화번호 5            | 67%  |
| 2차  | 카드s 30, 아이콘 17, 이미지2 12, 기간 12, 선택s 11, 문자s 11, 문자md 10                          | 92%  |

### 서버와 데이터

- 서버 코드는 모두 `base2/server`에 있다.
  - `/api/v0/[table]`: lowDB(JSON 파일). 개발용이다.
  - `/api/v1/[table]`: Supabase Postgres. **운영 데이터가 여기에 있다.**
  - 그 밖의 라우트: 파일(Supabase Storage), 채점, 토스 결제, AI(Gemini), sitemap.
- 캐시 무효화
  - 쓰기가 성공하면 `tables` 표에서 그 표의 `version`을 올린다.
  - 클라이언트는 1초 간격으로 버전을 확인한다.

### 권한과 로그인

- `server/middleware/api-guard.ts`가 `{table}:{read|create|update|delete}` 권한으로 판정한다. 권한이 없으면 403을 돌려준다.
  - 권한 정보는 `roles.permissions`에 있다.
  - `readPublic` 권한만 있으면 공개 필드만 준다.
- 화면 진입은 메뉴 행에 적힌 접근 역할로 막는다.
- `is관리자`(`useMyAuthStore`)와 `is처리자`(`model회원.ts`, `is관리자 || is담당자`)는 화면 표시에만 쓴다.
- 로그인은 Supabase Auth로 한다.
  - 구글, 카카오, 네이버 OAuth와 익명 로그인을 쓴다.
  - 역할은 Custom Access Token Hook이 토큰에 싣는다.
  - 개발 로그인은 `isDev`일 때만 열린다. 시드 이메일 4개만 통과한다.

### 보안 구멍 (이식본에서 막는다)

- **파일 삭제와 업로드**: `files/delete`와 `files/upload`는 `api-guard`를 거치지 않고, 라우트 안에서도 신원을 확인하지 않는다. 삭제는 service role 키를 쓰므로 누구나 아무 경로나 지울 수 있는 구조다.
  - 코드를 읽고 내린 판단이다. 실제 요청을 보내 확인하지는 않았다.
  - 운영 중인 원본의 문제이므로 이식과 별개로 먼저 막는 편이 좋다.
- learner가 신청 전체를 읽을 수 있다.
- guest에게 `enrolls:update`가 열려 있고, 행 소유자는 검사하지 않는다.
- manager의 "내 담당만" 제한은 화면에서만 거른다.

### 테마

- `app.config`의 색: primary 파랑, secondary 보라, neutral 슬레이트 등. 컴포넌트 33개의 기본 색을 neutral로 바꿔 둔다.
- 런타임 테마 축(`lib/theme/축.ts`)으로 색, radius, 폰트, 굵기, 크기, 대비 등을 바꾼다. 값은 쿠키에 두고, SSR 때 CSS 변수로 넣는다.
- `mTheme.css`는 면(surface) 토큰(`bg-page`, `bg-default`, `bg-muted`, `bg-elevated`)을 쓴다. `bg-white`와 `dark:`를 직접 쓰는 것은 금지한다.
- 폰트는 10종이고 기본은 Pretendard다.
- 아이콘 사용 횟수는 `i-lucide` 약 458회, `i-mdi` 약 320회, `i-ph` 72회, `i-material-symbols` 48회다. 원격 Iconify API로 받는다.
- 다크 모드는 기본값이 light이고, 사용자가 바꿀 수 있다.

  - 역할과 등급은 회원관계이력을 거쳐 얻는다.
  - 필터 6개, 정렬 6개, 요약 4개가 있다.
- 1만 건까지 늘 수 있는 표 (확인 필요)
  - 신청(`enrolls`)
  - 회원게시글(`member-posts`). 게시판 표(`boards`)는 아니다.
  - 회원댓글(`member-comments`)
  - 세 표 모두 지금은 전체를 읽은 뒤 메모리에서 거른다.

### 정리할 부채

- **위치·직업 코드**(`model회원.ts` 520–543): import하는 곳도, 가리키는 파일도 없는 죽은 코드다. `model직업`은 이미 폐기됐다.
- **setter의 비동기 결과를 기다리지 않는다**: `등급id`, `역할ids`, `afterSave`의 `do상태기록`, 메모·일정 태그 변경, 게시판 이동.
- **setter 안에서 confirm을 띄운 뒤 저장한다**: 역할과 등급의 `is기본옵션` setter가 confirm을 띄우고, 저장을 await 없이 부른다. 기존 기본 항목이 없으면 크래시한다.
- **`do순서정렬`**: 저장 두 건을 await 없이 부른다.
- **`상세.vue`**: 저장이 끝나기 전에 emit한다.
- **`any`**: `View/1.ts`에 약 40건(`type i필드 = any`), `ORM.ts`에 14건, `BaseModels2.view.ts`에 12건, `BaseModel2.ts`에 10건이 있다.
- **개발 계정**: admin과 admin_manager의 역할이 같아서 사실상 같은 계정이다.
- **원본 저장소 상태**: `BaseModels2.ts`에 커밋되지 않은 수정이 있다. 그 수정에 NUL 바이트가 섞여서 git이 이 파일을 바이너리로 본다.
