# 관리 모듈 이식: 계획서 작성 계획

이 문서는 실행 계획서(`docs/plans/admin-이식.md`)를 **어떻게 쓸지** 정한다.
계획서가 완성되고 합의되기 전에는 이식 코드를 쓰지 않는다.

## 배경

- 스타터의 CMS를 Payload 대신 자체 모델 기반 관리 화면으로 바꾼다.
  - 원본: admin.team-mjt.com (Nuxt), 소스는 `/Users/pc/Desktop/mWorkspace`
- 방향은 (가)로 정했다. Next.js로 이식하고, 모델만 정의하면 목록과 상세 화면이 자동으로 나오는 공통 모듈로 만든다.
- 이식은 필요한 것부터 차례로 한다.
  - 모델에서 많이 쓰는 Field부터 구현한다.
  - 최소한으로 작동하게 만든 뒤 테마를 옮기고 나머지를 채운다.

## 이미 확보한 사실

- base2 규모: m 약 16,200줄, View 약 7,400줄, composables 약 4,500줄, Field 약 4,400줄, lib/models 약 2,200줄. 합계 약 34,600줄.
- 모델이 화면을 선언한다: `자동필드ss`, `필터조건ss`, `정렬조건s`, `검색필드s`, `badges`, `요약s`.
- 조회는 클라이언트에서 검색 → 정렬 → 필터 순으로 한다. 필터는 다른 표를 이어 붙여 계산한 값에 거는 JS 함수다.
- 필드 컴포넌트는 `타입지정`으로 고르고, type이 없으면 값을 보고 판단한다. 판단 결과는 문자, 숫자, 체크, 날짜 가운데 하나다. (`lib/models/ORM.ts`)
- 모델 쪽 파일 80개에서 `타입지정` 사용 횟수 (합계 409):

### 모델 엔진 (`base2/lib/models`, 14개 파일, 2,154줄)

- 핵심 파일
  - `BaseModels2.ts`(694줄): 표 저장소. 목록, CRUD, 일괄 저장, SSR payload를 맡는다.
  - `BaseModel2.ts`(371줄): 행 모델. state, 저장, 수정됨 판정을 맡는다.
  - `BaseModels2.view.ts`(203줄): 조회와 URL 쿼리 변환.
  - `ORM.ts`(135줄): 타입 이름을 Field 컴포넌트로 바꾼다.
  - 그 밖에 `textSearch`, `identity`, `version`, `cachedRead`, `instance`, `env`, `types`, `seo`가 있다.
- 반응성
  - 원본 행은 Vue `Ref<Dto[]>`에 들어 있다.
  - `list`는 computed다. 삭제된 행을 빼고, 행마다 모델 객체를 한 번만 만들어 캐시하고, 정렬한다.
  - 행 객체는 바꿔 끼우지 않고 `Object.assign`으로 갱신한다.
- 로딩
  - `GET {api}/{table}`을 부른다. 본문 열은 `?omit=`으로 뺀다.
  - 표 버전이 같으면 다시 받지 않는다. 캐시는 TTL 5초다.
- 조회
  - `조회하기` 한 함수에서 검색 → 정렬 → 필터 순으로 처리한다.
  - 필터 축끼리는 AND, 한 축 안의 여러 선택은 OR다.
  - URL 쿼리(`?q=`, `?sort=`, `?f_<축>=`) 변환은 순수 함수여서 그대로 옮길 수 있다.
- 저장
  - 신규는 `POST`, 기존은 `PUT`, 일괄 저장은 `/bulk`로 보낸다.
  - 삭제는 목록에서 먼저 빼고, 실패하면 되돌린다.
  - 필드 단위 검증은 없고, `beforeSave()`가 유일한 관문이다.
- 폼
  - 필드 목록은 `View/1.ts`가 모델의 `자동필드ss`에서 만든다. `자동필드ss`가 없으면 getter/setter를 반사해서 만든다.
  - 컴포넌트는 이 순서로 고른다: `type` → `options`가 있으면 `선택0` → 값의 타입으로 판단 → 문자.
- Field 계약
  - `modelValue`와 `update:modelValue`로 값을 주고받는다.
  - `readonly`를 받는다.
  - `is-doing`은 선택 사항이다.
  - 나머지는 스펙의 `props`와 `items`로 받는다.
  - 버튼 필드는 값 없이 `onClick`, `label`, `icon`을 받는다.
- 원본 저장소의 `BaseModels2.ts`에 커밋되지 않은 수정이 있다. 그 수정에 NUL 바이트가 들어가서 git이 이 파일을 바이너리로 본다.

### 서버, 데이터, 권한

- 서버 코드는 모두 `base2/server`에 있다.
  - `/api/v0/[table]`은 lowDB(JSON 파일, 개발용)를 쓴다.
  - `/api/v1/[table]`은 **Supabase Postgres**를 쓴다. **운영 데이터는 v1에 있다.**
  - 그 밖의 라우트: 파일(Supabase Storage), 채점, 토스 결제, AI(Gemini), sitemap.
- 캐시 무효화
  - 쓰기가 성공하면 `tables` 표에서 그 표의 `version`을 올린다.
  - 클라이언트는 버전을 1초 간격으로 확인한다.
- 권한
  - `server/middleware/api-guard.ts`가 `{table}:{read|create|update|delete}` 권한으로 판정하고, 권한이 없으면 403을 돌려준다. 권한 정보는 `roles.permissions`에 있다.
  - `readPublic` 권한만 있으면 공개 필드만 준다.
  - 화면 진입은 메뉴 행의 접근 역할로 막는다.
  - `is관리자`는 `useMyAuthStore`에 있다. `is처리자`는 `model회원.ts`에 `is관리자 || is담당자`로 정의돼 있다. 둘 다 화면 표시용이다.
- 로그인
  - Supabase Auth로 구글, 카카오, 네이버 OAuth와 익명 로그인을 쓴다. 역할은 Custom Access Token Hook이 토큰에 싣는다.
  - 개발 로그인은 `isDev`일 때만 열리고, 시드 이메일 4개만 통과한다.
- 원본의 보안 구멍 (이식본에서 막는다)
  - 파일 삭제(`files/delete`)와 업로드 라우트는 `api-guard`를 거치지 않고, 라우트 안에도 신원 확인이 없다. 삭제는 service role 키를 쓰므로 누구나 아무 경로나 지울 수 있는 구조다.
  - learner가 신청 전체를 읽을 수 있다.
  - guest에게 행 소유자 검사 없이 `enrolls:update`가 열려 있다.
  - manager의 "내 담당만" 제한을 화면에서만 거른다.

### 테마

- `app.config`의 색은 primary 파랑, secondary 보라, neutral 슬레이트 등이다. 컴포넌트 33개의 기본 색을 neutral로 내린다.
- 런타임 테마 축(`lib/theme/축.ts`)으로 색, radius, 폰트, 굵기, 크기, 대비 등을 바꾼다. 값은 쿠키에 두고 SSR 때 CSS 변수로 넣는다.
- `mTheme.css`는 면(surface) 토큰(`bg-page`, `bg-default`, `bg-muted`, `bg-elevated`)을 쓰고 `bg-white`와 `dark:` 직접 사용을 금지한다.
- 폰트는 Pretendard를 기본으로 10종을 쓴다.
- 아이콘은 `i-lucide` 약 458회, `i-mdi` 약 320회, `i-ph` 72회, `i-material-symbols` 48회 쓰인다. 원격 Iconify API로 받는다.
- 다크 모드는 기본값이 light이고, 사용자가 바꿀 수 있다.

### 앱 구성

- admin.team-mjt.com은 `apps/mjt-admin`이 서빙한다.
- Nuxt layers로 `mjt-admin` → `base-mjt` → `base2`를 extends한다. 운영에서는 base-mjt와 base2를 github 저장소에서 받는다.
- 배포는 Netlify다.

### base-mjt 모델 (35개)

- 규모별 분포
  - 가장 크다: 회원게시글 1,418줄, 회원 754줄, 회원회비 715줄, 신청받기 700줄
  - 가장 작다: 기본 59줄, 투표 59줄, 설문 67줄
- **첫 대상 판단**: 역할(`roles`, 288줄)이 등급보다 단순하다.
  - 필터, 정렬, 검색, 요약이 없고, 배지는 "회원 N" 하나다.
  - 다만 두 기능이 다른 표에 기댄다.
    - "메뉴 관리" 버튼은 메뉴 표에 의존한다.
    - "API 권한" 선택지는 테이블 등록부에 의존한다.
  - 등급은 급수를 메뉴에서 계산하고, 등급요건과 심사 표에 의존한다.
- 회원(754줄)은 거의 모든 표에 의존한다.
  - 역할과 등급은 회원관계이력을 거쳐 얻는다.
  - 필터 6개, 정렬 6개, 요약 4개가 있다.
- 1만 건까지 늘 수 있는 표
  - 신청(`enrolls`)
  - 회원게시글(`member-posts`). 게시판 표(`boards`)가 아니다.
  - 회원댓글(`member-comments`)
  - 셋 다 지금은 전체를 읽고 메모리에서 거른다.
- 부채
  - **위치·직업 코드**(`model회원.ts` 520–543): import도 파일도 없는 죽은 코드다. `model직업`은 폐기됐다.
  - **기다리지 않는 setter**: `등급id`, `역할ids`, `afterSave`의 `do상태기록`, 메모·일정 태그 변경, 게시판 이동.
  - **setter 안의 confirm 후 저장**: 역할과 등급의 `is기본옵션` setter가 confirm을 띄운 뒤 저장을 await 없이 부른다. 기존 기본 항목이 없으면 크래시한다.
  - **`do순서정렬`**: 저장 두 건을 await 없이 부른다.
  - **`상세.vue`**: 저장을 기다리지 않고 emit한다.
  - **`any`**: `View/1.ts`에 약 40건(`type i필드 = any`), `ORM.ts`에 14건, `BaseModels2.view.ts`에 12건, `BaseModel2.ts`에 10건이 있다.
  - **개발 계정**: admin과 admin_manager의 역할이 같아서 두 계정이 사실상 중복이다.

### 현재 스타터 (mWorkspace2)

- 구성
  - `apps/web`: Next 16, React 19, Tailwind 4. 화면은 빈 페이지 하나와 `/api/health` 라우트뿐이다.
  - `packages/db`: Drizzle. 예시로 `users` 표 하나만 있다.
  - `packages/tsconfig`
- 문서와 맞지 않는 점
  - **Payload가 설치돼 있지 않다.** 바꿀 대상이 코드에는 없고 문서에만 있다.
  - **"스타터 구조 결정" 문서가 저장소에 없다.**
  - **design-system 패키지가 없다.** 테마 절은 CSS 변수를 둘 곳부터 정해야 한다.
  - 인증이 없다. 원본은 Supabase Auth를 쓴다.

4. 4~8절(엔진, 서버, 뷰, Field, 테마)을 쓰고 검토를 받는다.
5. 9~13절(순서, 부채, 단계, 위험, 체크리스트)을 쓰고 검토를 받는다.
6. 합의되면 "스타터 구조 결정" 문서의 CMS 항목을 바꾸고 계획서 링크를 건다.

## 완료 기준

- 계획서의 13개 절이 모두 채워져 있다.
- 단계마다 완료 기준과 검증 방법이 있다.
- 열린 질문이 모두 답을 받았거나, 누가 언제 정하는지 적혀 있다.
- 사용자가 계획서를 승인했다.
