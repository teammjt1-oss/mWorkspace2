# 스타터 구조 결정

2026-09-24 · 원문: [스타터 구조 결정](https://claude.ai/code/artifact/187bc9ab-d84b-46f9-b294-84f04c8fa7c0)

회사 스타터는 next-forge 구조를 참고해 `apps/web` + `apps/app` 두 앱과 규약이 통일된 `@repo/*` 패키지로 재편한다. 도구(bun, Prisma, Biome)와 20여 개 패키지 규모는 가져오지 않는다.

## 원칙

'형태'란 모든 기능의 위치가 미리 정해져 있고, 패키지가 같은 규약을 따르며, 그 규약이 CLAUDE.md에 적혀 있는 상태를 말한다.

| 사용 빈도 | 방식                        | 이유                                     |
| --------- | --------------------------- | ---------------------------------------- |
| 거의 항상 | 스타터에 포함               | CI가 계속 검증하고, 추가보다 삭제가 쉽다 |
| 가끔      | `docs/recipes/`에 절차 문서 | 쓰지 않는 코드를 끌고 다니지 않는다      |
| 안 씀     | 제외                        |                                          |

recipe는 CI가 검증하지 않아 조용히 낡는다. 그래서 설치할 패키지, 추가할 `keys.ts`, 연결 지점만 담아 짧게 유지한다. CLAUDE.md에서 recipe 위치를 안내한다.

## 골격

앱은 항상 있는 `web`(공개 영역)과 로그인 서비스 영역인 `app`으로 나눈다.

| 위치                         | 역할                                                                         |
| ---------------------------- | ---------------------------------------------------------------------------- |
| `apps/web`                   | 공개 사이트. 모든 프로젝트에 있다                                            |
| `apps/app`                   | 로그인 후 서비스 영역. `packages/auth`와 한 세트                             |
| `packages/design-system`     | shadcn 기반 공통 UI. web과 app이 함께 쓴다                                   |
| `packages/next-config`       | 공통 Next.js 설정, `NEXT_PUBLIC_WEB_URL`, `NEXT_PUBLIC_APP_URL`              |
| `packages/db`                | Drizzle + PostgreSQL, `keys.ts` 추가, `server-only` 적용                     |
| `packages/auth`              | Better Auth                                                                  |
| `packages/observability`     | `instrumentation.ts`의 `onRequestError`와 구조화 로그 함수                   |
| `packages/typescript-config` | 기존 `packages/tsconfig`의 새 이름. `base`, `nextjs`, `react-library` 프리셋 |
| `docs/recipes/`              | 가끔 쓰는 기능의 연결 절차                                                   |

패키지 규약:

- 각 패키지는 `index.ts`와 `keys.ts`를 두고, 필요하면 `server.ts`와 `client.ts`로 나눈다.
- `keys.ts`는 `@t3-oss/env-nextjs`와 zod로 환경변수를 검증한다.
- 각 앱의 `env.ts`는 쓰는 패키지의 keys를 `extends`로 합친다.
- 서버 전용 코드는 `server-only`로 막는다.

observability를 별도 패키지로 둘지, `next-config`에 합칠지는 구현할 때 정한다.

## 인증

Better Auth로 소셜 로그인만 지원하고, 기본 제공자는 구글과 카카오로 한다. 네이버는 필요할 때 켠다. 우리가 쓸 Better Auth 버전이 카카오와 네이버를 지원하는지는 구현할 때 확인한다.

- **계정 자동 병합:** 이메일이 같으면 합친다. 단, 제공자가 인증된 이메일이라고 확인해 준 경우에만 합친다. 이 조건이 없으면 남의 계정을 탈취하는 경로가 생긴다.
- **이메일은 식별자가 아니다:** 카카오는 사용자가 동의해야 이메일을 준다. 따라서 사용자 테이블에서 이메일에 unique나 not null을 걸지 않는다.
- **E2E 테스트 로그인:** 개발과 테스트 환경에서만 켜지는 테스트 로그인 경로를 둔다. 프로덕션에서는 env 검증으로 켜지지 않게 막는다.
- **이메일 발송은 필요 없다:** 소셜 로그인만 쓰므로 비밀번호 재설정이나 인증 메일이 없다.

## 벤더

벤더는 회사 전체에서 고정이다. recipe는 아래 벤더에 맞춘 구체적인 절차로 쓴다.

| 기능        | 벤더           | 빈도  | 방식                                          | 붙는 곳  |
| ----------- | -------------- | ----- | --------------------------------------------- | -------- |
| 배포        | Vercel         | 항상  | 스타터에 포함                                 | web, app |
| 에러 추적   | Sentry         | 가끔  | 기본 장치는 스타터, 연결은 `observability.md` | web, app |
| 결제        | 토스페이먼츠   | 가끔  | `payments.md`                                 | app      |
| 파일 저장소 | Vercel Blob    | 가끔  | `storage.md`                                  | 주로 app |
| CMS         | Payload (잠정) | 가끔  | `cms.md`                                      | 주로 web |
| 이메일      | 보류           | 가끔  | 지금은 recipe도 만들지 않음                   |          |
| 분석        | 없음           | 안 씀 | 제외                                          |          |

결제 recipe는 고객사가 토스페이먼츠와 계약한 경우를 전제로 한다. 다른 PG와 계약한 경우는 프로젝트별로 따로 처리한다.

## 배포와 계정

앱마다 Vercel 프로젝트를 하나씩, 총 2개 만들고 모든 벤더 계정은 당분간 회사 명의로 운영한다.

- 각 Vercel 프로젝트에 Root Directory를 지정하고, `turbo-ignore`로 변경이 없는 앱은 빌드하지 않는다.
- production, preview, staging 환경변수를 어디에 넣는지 배포 문서에 적는다. 입력은 우리 팀이 하므로 문서는 우리 팀이 따라 하는 절차로 쓴다.
- `/deploy-staging` skill, CI, E2E를 두 앱 기준으로 바꾼다.
- 명의가 고객사로 바뀔 수 있으므로 각 recipe의 "계정 만들기" 단계는 별도 섹션으로 둔다. 이관 절차가 필요해지면 그 섹션만 고친다.
